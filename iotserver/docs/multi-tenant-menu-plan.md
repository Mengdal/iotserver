# 多租户 · 菜单与租户管理 设计规划

> 范围：本轮讨论确定的事项 —— ① 菜单的"全局 + 租户自定义/覆盖"模型；② 菜单管理的权限收口；③ 租户管理当前缺口（删租户、配额、到期）；④ 平台视图创建业务数据的兜底。
>
> 状态：**P0 + P1 已实现**（菜单多租户、租户管理三缺口、前端配套）；详见 §9 实现状态。
> 已实现的不再重复规划（如"权限字符同租户内唯一"，见 §7）。

## 1. 现状与问题清单

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| 1 | `sys_menu` 是全局表，**租户管理员也能改/删全局菜单** | 菜单写接口只校验 `menu:add/edit/remove`，而租户管理员天然拥有这些权限；实测用 `demo_a_admin` 成功建出全局菜单、平台管理员立刻可见 | 租户可影响其他租户的侧边栏 |
| 2 | 租户**无法**"只给自己隐藏/改名"某个平台菜单 | 只能改全局那一行 | 一改就串，功能上等于不可用 |
| 3 | 平台改菜单后，无法感知"有哪些租户做了定制" | 无覆盖层 | 改名/删除时心里没底 |
| 4 | **删租户不级联**：只删 `tenant` 行 | `deleteTenant` 仅删 `tenant` 表 | 该租户用户仍可登录、数据仍在，租户名查不到 |
| 5 | 配额字段（设备/网关/用户）**只存不校验** | `MaxDevices/MaxGateways/MaxUsers` 仅出现在 tenantapp 的读写里 | 超配额照样能建 |
| 6 | 到期时间 `expireAt` **只存不校验** | 同上 | 过期租户仍可登录使用 |
| 7 | 平台视图创建业务数据无归属，无任何提示 | GORM 插件在 `Platform` 作用域下不写 `tenant_id` → 落成 `tenant_id=''`；用户实测建出"孤儿产品" | 以为租户能看到，其实看不到 |
| 8 | 菜单管理的"当前编辑范围"不可见 | 平台管理员一旦切到某租户再进菜单管理，无法分辨改的是全局还是该租户 | 易误改全局 |

### 目标分层（行业共识，也是本次设计的基线）

```
① 租户隔离（最外层）   谁的数据        tenant_id 行级过滤           ← 已实现
② 功能权限（菜单/按钮） 能用哪些功能    角色 → 菜单授权              ← 已实现
③ 数据权限（数据范围） 能看哪些行       DataScope 1/2/3/4            ← 字段已存，未生效
④ 菜单归属与定制        菜单长什么样    全局菜单 + 租户自定义/覆盖    ← 本次设计
```

## 2. 菜单模型设计

### 2.1 数据模型

**改动 1：`sys_menu` 增加 `tenant_id` 列**

```
sys_menu.tenant_id = ''   → 平台原始菜单（只有平台管理员能写）
sys_menu.tenant_id = 'X'  → 租户 X 的自定义菜单
```

约定（与现有 `sys_config`、`solution` 的"全局默认 + 租户覆盖"一致）：
- **不**登记进 `models.tenantScopedModels`（登记了会连全局行一起被过滤掉），由应用层显式处理；
- 所有菜单查询显式带上 `tenant_id IN ('', 当前租户)`；平台视图只看 `''`。

**改动 2：新增租户覆盖表 `tenant_menu_pref`（展示层覆盖）**

| 列 | 说明 |
|---|---|
| `tenant_id` | 租户 |
| `menu_id` | 指向 `sys_menu.id`（全局菜单或本租户自建菜单） |
| `hidden` | 1 = 本租户隐藏该菜单（含其子级） |
| `custom_name` / `custom_icon` | 本租户自定义展示（可空 = 跟随全局） |
| `sort` | 本租户自定义排序（0 = 跟随全局） |

唯一索引 `(tenant_id, menu_id)`。**只覆盖展示属性，绝不覆盖 `path` / `perms` / `component`** —— 否则平台修路径、修权限 bug 时租户会永远卡在旧配置上。

### 2.2 读取合并规则

```
本用户可见菜单 =
    ( 全局菜单(tenant_id='') ∪ 本租户自建菜单(tenant_id=X) )
  − 本租户隐藏项(tenant_menu_pref.hidden=1，含其子树)
  ∩ 角色授权(sys_role_menu，管理员角色=全量)
  − platform_only 菜单（仅对租户用户，现有逻辑不变）
→ 套用 custom_name / custom_icon / sort → 补全父级 → 建树
```

落地要点：
- 现状 `roleMenusByUserId` 是**原生 SQL**（`sys_menu ⋈ sys_role_menu ⋈ sys_user_role`），绕过 GORM 插件 → **租户条件必须手写进这条 SQL**；
- 管理员分支 `menusOfUser(admin=true)` 现状是 `SysMenuAll()` → 改为"`tenant_id IN ('', X)` 的全量"（平台管理员仍是 `tenant_id=''`）；
- `tenant_menu` 不需要新的"角色→菜单"映射表：租户自建菜单与全局菜单共用 `sys_menu.id`，`sys_role_menu` 原样复用。

### 2.3 写入归属规则（**最容易出事故，必须明确**）

| 谁 · 在什么视图 | 写入目标 | 影响范围 |
|---|---|---|
| 平台管理员 · 平台视图（不带 `x-tenant-id`） | `sys_menu.tenant_id=''` | **全局** |
| 平台管理员 · 代管租户 X（带 `x-tenant-id`） | `tenant_id='X'` 的自建菜单 / X 的 `tenant_menu_pref` | 仅租户 X |
| 租户 X 的管理员（有菜单管理权限） | `tenant_id='X'` 的自建菜单 / X 的 `tenant_menu_pref` | 仅租户 X |

服务端强制（不能只靠前端）：
- 目标租户 = `tenant.FromContext(ctx)`：`Platform=true` → `''`；否则取 `TenantID`；
- 更新/删除前校验**该行归属**必须等于目标租户；
- 目标为 `''` 时必须 `IsPlatformAdmin`（否则返回权限不足）。

### 2.4 菜单管理页交互

- 顶部**显式提示当前编辑范围**：「当前编辑：平台原始菜单」/「当前编辑：租户A 的自定义菜单」；
- 平台视图：只列 `tenant_id=''`，常规增删改；
- 代管/租户视图：
  - 「本租户自定义菜单」页签 —— 可增删改；
  - 「平台菜单」页签 —— **只读**，每行提供「隐藏 / 改名 / 排序」（写 `tenant_menu_pref`），不提供"编辑/删除本体"；
- 删除全局菜单时给出**影响面提示**："被 N 个租户隐藏/改名，M 个租户在它下面挂了自建菜单"。

### 2.5 删除与升级规则

| 场景 | 规则 |
|---|---|
| 平台删除全局菜单，且有租户自建子菜单挂在它下面 | **禁止删除**，提示数量（避免孤儿菜单）；建议改用"停用" |
| 平台删除全局菜单，仅有租户覆盖记录 | 允许，**级联清理该菜单的 `tenant_menu_pref`**，并记日志 |
| 平台改名/换图标/排序 | 未覆盖的租户立刻跟随；已改名覆盖的租户保留自己的展示 |
| 平台改 `path`/`perms`/`component` | **所有租户立刻跟随**（覆盖不含技术属性） |
| 平台停用/隐藏全局菜单 | 所有租户立刻不可见；**租户不能反向恢复**（安全考虑） |
| 平台新增菜单 | 所有租户自动可见（无需回填） |
| 平台"重置某租户菜单定制" | 提供 `POST /menu/tenant-reset`：清空该租户的 `tenant_menu` + `tenant_menu_pref`，恢复平台默认 |

### 2.6 权限码

| 权限码 | 用途 |
|---|---|
| `menu:list` / `menu:query` | 读（保留给租户，角色分配菜单要用） |
| `menu:add` / `menu:edit` / `menu:remove` | **写菜单本体**：目标为 `''` 时额外要求平台管理员；目标为 `X` 时要求属于 X |
| `menu:custom:pref`（新增） | 写 `tenant_menu_pref`（隐藏/改名/排序） |
| `menu:custom:reset`（新增） | 平台重置某租户的菜单定制 |

> 「菜单管理」菜单本身保持非 `platform_only`（租户要能管自己的菜单），但**改全局本体在接口层被平台管理员限制**。

## 3. 租户管理缺口设计

### 3.1 删租户保护（P0）

- 删除前统计该租户下的 **用户 / 设备 / 网关 / 产品 / 看板** 数量：
  - 有数据 → **拒绝删除**，返回"该租户下仍有 N 个用户、M 台设备…，请先清理"；
  - 无数据 → 允许删除（并清理其 `tenant_menu` / `tenant_menu_pref`）。
- 可选增强：平台管理员带 `force=true` 时，**级联禁用该租户全部用户**后再删除（数据保留但不可登录），并记审计日志。

### 3.2 配额校验（P1）

- 在 `设备 / 网关 / 用户` 的**新增入口**校验：`max* == 0` 视为不限；否则 `当前数量 + 1 > max` → 拒绝并给出明确提示；
- 计数必须在**目标租户**作用域内统计（代管视图下按被代管租户计）；
- 建议同时在上层提供一个"租户资源用量"查询接口，供租户管理页展示"已用/上限"。

### 3.3 到期校验（P1）

- **登录时**：`expireAt > 0 && now > expireAt` → 拒绝登录，提示"租户已到期，请联系平台管理员"；
- **请求时**（更稳）：租户用户的请求在中间件里再校验一次，避免"登录后被延期/停用"的会话继续可用；
- 平台管理员不受影响。

## 4. 平台视图创建业务数据的兜底（P2）

现状：平台管理员在平台视图建产品/设备/网关 → `tenant_id=''`，租户看不到（§1 问题 7）。

- **前端（先做）**：平台视图（`currentTenantId` 为空）点新增时弹确认："当前是平台视图，创建的数据不属于任何租户，租户看不到；如需归到租户请先切换「当前租户」"，提供"去切换"按钮；
- **后端（可选，更硬）**：对 `产品/设备/网关` 的新增，若上下文为 `Platform` 且请求未显式指定租户 → 拒绝并提示。**默认不做**，避免影响平台自用资产/离线导入场景。

## 8. 风险与开放问题

**风险**
1. `sys_menu` 加 `tenant_id` 后，历史上"用 `SysMenuAll()` 当全量菜单"的地方（权限收集、菜单树、角色分配）都要审计一遍，漏一处就会出现"租户看到别人的菜单"或"看不到自己的菜单"；
2. `roleMenusByUserId` 是原生 SQL，容易漏改；
3. 覆盖层与 seed 的交互：seed 每次启动会 upsert 全局菜单，**不得覆盖租户的 `tenant_menu_pref`**（设计上 prefs 独立成表，天然隔离，但要写测试锁住）。

**开放问题（待你确认）**
1. 租户自建菜单的 `perms` 字段：**建议不允许填**（否则等于自助提权），或者只允许填"该租户已拥有权限码的子集" —— 你选哪个？
2. 租户自建菜单建好后：**需要分配给角色才可见**（建议，与全局菜单一致），还是**建完自动对本租户可见**？
3. 是否允许把租户自建菜单**挂在平台菜单下面**（如挂在「数据中心」下）？建议允许。
4. 是否需要"个人级"菜单偏好（每个用户自己隐藏/排序，行业里叫自定义工作台）？建议先不做。
5. 是否要按**套餐**卖不同功能（基础版/高级版）？若需要，菜单读取还要再叠一层"套餐 ∩ 角色"，建议提前预留 `sys_tenant_package` + `tenant.package_id` 字段。
